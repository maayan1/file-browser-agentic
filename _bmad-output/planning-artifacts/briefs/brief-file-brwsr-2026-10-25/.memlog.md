- (decision) Intent: Create a new brief. Coaching path chosen by the user (interactive, questions in small groups, trade-offs explained); no PRD and no code yet.
- (event) Sources: docs/product/file-browser-idea.md (6 features), docs/product/earsRequirments (3 EARS reqs), docs/product/smsrtlocalbrowser (user prompt, 10 features + constraints). Feature list and constraints captured in addendum.
- (decision) Product name is 'Smart Local File Browser' (the user's prompt); the project config name 'File Brwsr' is only the folder label.
- (decision) Hard constraints: browser-only, no backend, no network during use, read-only, no persistence of contents or metadata, framework-independent core logic.
- (event) Feature scope grew from 6 (idea doc) to 10 (prompt): added type filter, locate result in tree, PDF/text preview, list/thumbnail toggle, sort by type/size/date.
- (event) Research digest in addendum. showDirectoryPicker works only in Chromium; Firefox and Safari need webkitdirectory (eager full-tree walk) or drag-and-drop. Native explorers beat a browser app on core features; the plausible differentiator is cross-browser, read-only, and stateless together.
- (decision) Stakes: portfolio project that will also go to real users. Top priorities are practicing BMAD and building a clean architecture, so market rigor stays medium.
- (decision) Primary user (tentative): people who search for files many times a day as part of their work, e.g. secretaries, developers, scientists. Defined by behaviour, not role; still too broad, needs a concrete scenario.
- (decision) Why a browser (user's words): a 'unique system' (meaning to confirm: the same tool on any OS?) and room for smart features, including talking to the computer and getting replies.
- (event) Tension: conversational AI conflicts with 'no network during use' (cloud LLM) and with cross-browser (on-device LLMs are mostly Chromium-only and heavy). Raised with the user.
- (event) Tension: frequent searchers with no persistent storage means rescanning or reindexing every session, which is slower than the OS's indexed search. Raised with the user.
- (decision) Conversational AI moved out of the MVP into Vision (option C). MVP 'smart' must work without a model, offline, and in every browser; a structured-query interface keeps an AI adapter possible later.
- (decision) MVP smart features: forgiving search (typos, partial words, split names), version clusters, and content search. Rejected for MVP: query shortcuts, session memory, folder insights; smart ranking was not chosen.
- (decision) Browsers: Chrome and Edge only (Chromium, File System Access API). 'One consistent system' now means the same tool on any desktop OS via Chromium. Firefox and Safari are out of the MVP.
- (event) Consequence: going Chromium-only gives up the 'cross-browser + read-only + stateless' gap from research (the closest comparable is also Chromium-only). Differentiation now rests on read-only, stateless, version clusters, and forgiving/content search.
- (event) Open: version-cluster rule (risk of false groups, e.g. invoice_01/invoice_02), content-search scope (file types, size limits, in-memory index each session), ranking needed to make fuzzy results usable, concrete search scenario still not given.
- (decision) Ranking is part of forgiving search (exact, then partial, then typo match), not a separate feature.
- (decision) Product principle: a smart feature must never hide the right file. For a frequent searcher, that is worse than having no feature.
- (decision) Version clusters use strict rule (a): group only names with a recognized marker (v1/v2, final, copy, (1), draft, date), across folders, never hiding files; shown as 'possible versions'.
- (decision) Content search in the MVP covers text files only. The user asked me to suggest a rule for adding PDF, Word and Excel later.
- (event) Hero scenario from the user: a student (or anyone) looking for all of last year's invoices, or the invoices from a specific year.
- (event) Conflicts the scenario exposed: invoices are usually PDFs, which text-only content search misses; 'date' as a version marker would wrongly group invoice_2024-01 and invoice_2024-02; finding invoices by year needs a date/year filter; tax-season searching is occasional, not daily.
- (decision) Added a date-range filter (from date to date) as a basic filter next to the type filter.
- (decision) Content search in the MVP: text files plus PDFs (my reading: PDFs with a text layer, no OCR; pending user confirmation). Replaces the earlier text-only decision so the invoice scenario works.
- (event) User idea: when a file name contains a date, use file metadata to tell files apart. Concern: metadata such as size or mtime cannot reliably separate versions from distinct dated documents. Proposed instead: drop dates as version markers and let name dates feed the date filter.
- (event) User pasted a full PRD draft titled 'NXUSR', with no message of their own. Treated as source material: brief comes first, PRD later. Its decisions extracted below; the full text is kept in this conversation, and a pointer is in the addendum.
- (decision) Confirmed (via the PRD draft): content search covers TXT, MD, CSV, JSON, plain-text code and text-layer PDFs; no OCR; in-memory index cleared at session end; name results appear before content indexing finishes.
- (decision) Confirmed: dates are not version markers. Smart date filter (year or custom range) matches if either a date in the file name or the mtime falls in range, and shows which date matched.
- (decision) Adopted six product principles: never hide the right file; privacy by design; user control; search first; performance first; transparent results (confirmed vs estimated).
- (event) New candidate name 'NXUSR' (not yet confirmed). Scope jumped to 12 mandatory MVP features, adding three never discussed: SHA-256 duplicate detection, file comparison (diff + similarity score), and cleanup recommendations.
- (event) Dropped from the earlier list without discussion: list/thumbnail view toggle, locate a search result in the tree, image preview (now generic 'previews'). Network rule softened to 'no network for file processing once resources are loaded'.
- (event) Tensions: hashing every file each session conflicts with 'performance first' plus statelessness; cleanup advice in a read-only app cannot be acted on in the app and serves a second job (tidying) rather than 'search first'. Primary user still not chosen (PRD lists 5 groups).
- (decision) MVP cut: duplicate detection and cleanup recommendations move to Future. MVP = tree/navigation, forgiving search with ranking, type + smart date filters, preview, text+PDF content search, version clusters, and comparing files within a version cluster.
- (decision) Primary user: someone who looks for files on their computer throughout the workday and keeps receiving new ones (reports, analyses, invoices). Main pain: finding the right file in a growing collection without remembering its exact name or location.
- (decision) NXUSR was a typo, not the name. The user wants a catchy, memorable name about smart, human-friendly search (in the spirit of 'Smart Human Search'). Working title stays 'Smart Local File Browser' until chosen.
- (assumption) Locate-in-tree and preview (images, text, PDF) stay in the MVP because they serve 'search first'; the list/thumbnail toggle moves out of the MVP. Tagged [ASSUMPTION] in the draft for the user to confirm.
- (event) Risk raised: this user's incoming files often land in Downloads/Desktop, and the spec lets Chromium block picking those folders (and the home folder) directly. Needs verification and a UX answer.
- (event) Drafted brief sections: The Problem, Who This Serves, Product Principles.
- (decision) Downloads-block mitigation (user's choice): users create a dedicated folder, point the browser's download location at it, and grant the app access. Pushback: it misses attachments saved by desktop mail and chat apps and depends on habit change. Possible alternatives to verify: subfolders of Downloads, or drag-and-drop, which the spec exempts from the blocklist.
- (decision) Name direction: professional, powerful, memorable; conveys precise, deep, thorough discovery that finds files other search tools miss, even from partial or inaccurate memory. Playful options (Hunch, Kinda, Rummage...) rejected.
- (assumption) The user has not answered on dropped features or reviewed the first sections; the assumptions stand (keep locate-in-tree and preview; list/thumbnail toggle out).
- (event) Drafted brief sections: The Solution, What Makes This Different, Scope, Open Risks and Unknowns.
- (decision) Product name: 'Find' (the user's choice over Quarry/Argus). Concerns raised: a generic word that is hard to search for, trademark, or tell apart from Finder, the find command, and Ctrl+F; it doesn't signal 'deep/precise'. Brief updated to use it.

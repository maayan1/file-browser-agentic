# PRD Quality Review — PRD: Find

- **PRD:** `_bmad-output/planning-artifacts/prds/prd-file-brwsr-2026-10-25/prd.md` (status: final) + `addendum.md`
- **Rubric:** `.claude/skills/bmad-prd/assets/prd-validation-checklist.md`
- **Calibration:** portfolio project with real users; browser-only, read-only, stateless local file search for Chrome and Edge; about 8 pages; chain-top (feeds UX, architecture, stories).
- **Prior review:** `review-rubric-prefinal.md`. Its findings were checked against the current text; status is in Mechanical notes. They are not re-flagged unless still wrong.

## Overall verdict

This is a strong, build-ready PRD. The thesis is explicit and tested by the metrics (SM-1 now forces content and name-date tasks, SM-3 isolates content search). The Glossary is disciplined, scope cuts are honest, and every high and medium finding from the pre-final review is resolved. What remains is concentrated in the matching rules that stories and tests will lean on hardest. FR-10's headline acceptance example (`reprot` → `report`) fails under standard edit distance with the stated 1-edit limit, so "edit" must be defined. How a query is split into query words is undefined. The "exact" definition and EARS-01 use substring language that FR-9's token rules don't honor. Separately, two product bets go unmeasured: the MyFiles strategy rests on an unverified platform premise, and queries that mix a name cue with a content cue, which is the core job, match nothing. None of this blocks UX. The matching items should be settled before stories are written.

## Decision-readiness — strong

Decisions are stated as decisions and paired with their cost. The read-only stance (§1, NFR-2), no persistence (NFR-3, with OQ-5 naming the one exception that might be justified), the deferral of version clusters despite being "the brief's strongest differentiator" (§7.2 `[NOTE FOR PM]`), and the reversal to a smart date filter (addendum, Rejected alternatives) all show what was given up. FR-2 now handles the cancel-versus-blocked ambiguity honestly, and the addendum explains why. Open Questions are genuinely open and each has a validation path (OQ-3 and OQ-5 to SM-1, OQ-4 to SM-2 and SM-C1).

### Findings
- **medium** The MyFiles decision rests on an unverified premise and has no success signal (§3 MyFiles folder, FR-1, FR-2 Notes, OQ-1). The MyFiles folder is "the chosen answer to blocked folders", and OQ-1 says "This no longer blocks UX". But OQ-1's first open item is whether Chrome and Edge can open "a `MyFiles` folder inside Documents on Windows, macOS, and Linux" at all, so the decision's foundation is still unverified. The strategy also asks users to change their browser's download location, which sits uneasily with Principle 7 ("find a file without any onboarding or instructions"), and it only gathers *future* downloads, while UJ-1's Daniel has documents that "pile up across many folders" today. No SM measures whether users complete or benefit from the setup: SM-1 uses a seeded folder. *Fix:* state the fallback if the OQ-1 spike fails (for example, the guide recommends another location, or drops the download-location step). Note that the guide is optional and that Principle 7 is satisfied without it. Optionally, record in SM-1 whether participants would adopt MyFiles, next to the OQ-5 re-selection question.

## Substance over theater — strong

One persona, and Daniel drives real requirements: progressive loading, the smart date filter, preview-to-confirm, and the "content not searchable" labels. The NFRs carry product-specific thresholds and verification methods (NFR-1 to NFR-4). NFR-8 is now phrased as an outcome. The Vision's "MVP has one job" paragraph is a falsifiable bet that couldn't be dropped into another PRD. The §1.1 principles earn their place, because each one points to the FR or NFR it settles (Principle 1 to FR-12 and FR-16, Principle 4 to FR-11, FR-15 and FR-18). The counter-metrics are specific to this product (SM-C3's `ticket_20251`). No findings.

## Strategic coherence — strong

The thesis (§1 ¶3) drives the order: name search, content search, filters, then preview to confirm. The primary metrics now validate both halves of it. SM-1 requires "at least 2 of the 5 tasks [to be] solvable only through content or a name date" and is within-subject and counterbalanced. SM-3 isolates content search. Each counter-metric is tied to the SM it balances. The MVP is problem-solving in kind, and the scope logic matches.

### Findings
- **medium** Queries that mix a name cue and a content cue match nothing (§3 Name match, Content match; FR-9, FR-14; §2.1 Core job). The core job is "describe what I *do* remember". A name match needs *every* query word in the name, and a content match needs *every* query word in the content. So `budget q3`, where "q3" is in the name and "budget" is only in the text, is neither, and the right file is absent from the result list. Nothing in §6 or §7.2 says this is intended, and it directly affects SM-1's half-remembered-cue tasks. It also bears on Principle 1 ("Never hide the right file"). *Fix:* either decide that a query word may be satisfied by the name *or* the content (and give that case a match kind and a rank), or list "queries that mix name words and content words" in §7.2, and add a mixed-cue query to OQ-3 or the SM-1 task design so the gap is measured.

## Done-ness clarity — adequate

This dimension improved most since the pre-final review. Match kinds are defined per query word, tokenization covers camelCase and letter/digit boundaries, the empty-query-with-filter state is defined, rank with no query is defined, and performance has a reference machine, a scale ceiling, and a memory budget. FR-9, FR-11, FR-12 and FR-18 now read as acceptance criteria. What keeps this at *adequate* is that the matching rules, which FR-8 to FR-11, SM-2, SM-C1 and OQ-4 all rest on, still have three gaps that a developer will hit on day one.

### Findings
- **high** "Edit" is undefined, and FR-10's own headline example fails under the usual definition (FR-10, FR-11, UJ-1 step 2, SM-2). `reprot` has 6 letters, so it "tolerate[s] 1 edit". Turning `reprot` into `report` is one *transposition*, but under plain Levenshtein distance it costs two substitutions. So FR-10's first consequence ("`reprot` matches `report.pdf`"), FR-11's typo example, and UJ-1's headline query all fail if the developer chooses the most common algorithm. The PRD also doesn't say whether typo tolerance applies against a token's beginning: does `reprot` match the token `Reports` in `Q3_Reports.pdf`? Under any whole-token distance it doesn't. SM-2 and SM-C1 results, and the OQ-4 tuning, depend on both answers. *Fix:* in FR-10, define an edit as an insertion, deletion, substitution, or swap of two adjacent letters (Damerau / optimal string alignment distance). State whether a typo-tolerant query word can match a token's beginning, and add one acceptance example either way (for example "`reprot` matches `Q3_Reports.pdf` labelled typo", or "does not").
- **medium** How a query is split into query words is undefined (§3 Query, FR-9). The Glossary says the query "is split into **query words**" but not by what. Name tokens split at spaces, `_`, `-`, `.`, case changes, and letter/digit boundaries. If query words split only at spaces, then typing `project_report`, `ProjectReport`, or `Q3` becomes one query word that matches no single name token, so pasting or retyping a real file name can fail. *Fix:* state that the query is split by the same rules as name tokens (or name the difference), and add an acceptance example: "`project_report` matches `Project Report.pdf`".
- **medium** "Exact" uses substring language that the matching rules and EARS-01 don't agree on (§3 Match kind; FR-8 EARS-01; FR-9). "Exact" is "the whole query appears in the name". EARS-01, which §0 says this PRD carries as an acceptance test, requires names that "contain the search term". FR-9 instead matches only whole tokens or token beginnings. For `port` against `report.pdf`, the substring rules say match (and "exact"), while FR-9 says no match (`port` is not a token beginning, and it is 2 edits from `report`). The EARS-01 acceptance fixture passes either way, so the divergence is invisible to its test. *Fix:* state that only name matches (FR-9) receive a match kind, and that "exact" means the query, ignoring case, appears in the name *and* the entry is a name match. In FR-8, note that the PRD deliberately narrows EARS-01's "contain" to token and token-beginning matching, and add a negative example (`port` does not match `report.pdf`).
- **medium** The indexing target has no workload definition (NFR-4, SM-5). "1,000 mixed text files and text-layer PDFs … within 60 seconds" fixes the count but not the sizes or the mix. 1,000 PDFs near the 10 MB limit and 1,000 small `.md` files differ by orders of magnitude, so the target can't be tested and can't guide architecture. *Fix:* define the SM-5 fixture: share of PDFs, median and maximum file size, and total bytes (for example "≤ 500 MB total, 30% PDFs, median 200 KB").
- **low** Behavior above 50,000 file entries is undefined (NFR-4). "Folders larger than that are not supported in the MVP, and Find says so" doesn't say whether Find stops reading, loads the first 50,000, or refuses the folder, or whether name search and indexing run. *Fix:* one consequence, for example "Find stops at 50,000 file entries, shows a notice suggesting a subfolder, and searches only what was loaded".
- **low** Name-date edge cases are open (FR-18, SM-7, SM-C3). "Standalone year" isn't tied to name tokens, which `ticket_20251` (SM-C3) depends on. Names with two dates (`report_2024-01_to_2024-03`) have no rule. The addendum's "accept only valid calendar dates; `2025-13-45` is not a date" is a product rule that SM-7 tests, but it lives only in the addendum. *Fix:* define "standalone" as "a name token of exactly four digits", say which date wins when there are several (or that any date counts for the filter), and move the valid-calendar-date rule into FR-18.
- **low** The accessibility scope for previews is unclear (NFR-6, FR-20). "Fully usable by keyboard, and meet WCAG 2.1 AA" for "the preview" covers PDFs rendered page by page and arbitrary user images that have no alt text. Read literally, this needs an accessible PDF text layer, which is a significant architecture input. *Fix:* scope it, for example "preview controls and text-file previews meet WCAG 2.1 AA; PDF and image previews are keyboard-operable, with the file name as the accessible label".
- **low** "Filters hide N matches" is ambiguous with an empty query (FR-12). With no query there are no matches, yet the filtered-out notice "applies whether the visible result list is empty or not". *Fix:* say that with an empty query the count is of file entries hidden by the filters, or that the notice only appears when there is a query.

## Scope honesty — strong

§6 Non-Goals and §7.2 Out of Scope do real work, including the less obvious cuts: day-first name dates, full on-disk paths, one selected folder per session, and the DOCX → XLSX → OCR order. The `[ASSUMPTION]` tags are consistent and fully indexed (see Mechanical notes). §10 now says which defaults architecture should treat as fixed (FR-14, NFR-4). Open-items density is about 18 assumptions and 6 live OQs, which is fine for a portfolio-stakes PRD because none is marked as blocking, and the one with real reach (OQ-1) is scoped to an architecture spike. The one silent omission found (mixed name-and-content queries) is under Strategic coherence.

### Findings
- **low** §0 promises a "Blocks" marker that no OQ carries (§0 How to read it; §9). §0 says "Open questions that block a later phase are marked **Blocks** in §9", but §9 uses only "Informs", and OQ-1 explicitly "no longer blocks UX". Readers will look for the marker. *Fix:* say in §0 that no open question currently blocks a phase, or mark OQ-1 as blocking the architecture spike if that is the intent.

## Downstream usability — strong

The Glossary now covers every load-bearing noun the pre-final review flagged (start state, content-only match, match kind, selected file entry, text-layer PDF, location, blocked folder), and the FRs use them. Rank is defined once in §3, and FR-11 points to it. FR, NFR, SM, and SM-C IDs are contiguous and unique, the §7.1 FR ranges resolve, and UJ-1 steps are referenced precisely from each feature description. EARS sources are cited (§0), and the file exists at `docs/product/earsRequirments`. Each feature section reads on its own.

### Findings
- **low** Residual synonyms of Glossary terms (§1, §2.2, UJ-1 step 4, §4.5, FR-1, FR-4, NFR-3, NFR-4, OQ-5). "Results" / "name results" stands in for the result list or file entries in it (§1 "Results are ranked best first"; UJ-1 and §4.5 "too many results"; NFR-4 "name results appear"). "Folder access" (§2.2, FR-4) and "folder permission" (FR-1, NFR-3, OQ-5) sit next to the defined **read-only access**. Story extraction will copy them. *Fix:* replace "results" with "the result list" where it refers to the list, and use "read-only access" (or add "folder permission" to the Glossary as the persisted browser handle OQ-5 is about, which is a distinct concept).

## Shape fit — strong

A single-persona consumer utility with one rich UJ, edge cases folded into it, and no journey theater is the right shape. Implementation detail (`showDirectoryPicker`, `AbortError`, pdf.js, Web Workers, `FileSystemDirectoryHandle`) stays in the addendum, and the main body leaks almost none. At about 8 pages it is the agreed length. As a chain-top PRD it carries the traceability downstream needs without over-formalizing. No findings.

## Overall verdict

This is a strong, build-ready PRD, and better than the version reviewed in `review-rubric-v1.md`. The edits closed every high finding in the rubric and EARS reviews. Typo distance is now defined (Damerau-Levenshtein, OSA). Query words are split by the same rules as names. A **substring** match kind honors EARS-01's "contain". EARS-03 rev. 1 and EARS-04 are traced in §0 and carried by FR-12. The deliberate DOCX trade-off now reads the same way in the Vision, §2.2, UJ-1, FR-16, §7.2, and SM-1, so it counts as an accepted risk rather than a defect. The new match kinds, rank order, and FR examples agree with one another; every worked example checks out. What remains at risk is narrower. The **substring** tier has no minimum word length and ranks above **content**, so short queries can still bury the content matches the thesis depends on. FR-22 doesn't say what happens to the existing result list during a full rebuild. FR-21's open-in-tab can't keep NFR-5's promise for PDFs, and the UJ-1 hand-off relies on pasting a relative location into File Explorer, which is unverified. None of this blocks UX, but FR-10, FR-21, and FR-22 should be tightened before stories are written.

## Strategic coherence — strong

The thesis is now narrower and fully coherent with scope and metrics. "Forgiving, content-aware search … faster than OS search, for text files and PDFs" lines up with FR-14 and FR-16 (covered formats), SM-1's task design (content cues only in supported formats; at least 2 of 5 tasks solvable only through content or a name date), and SM-3, which isolates content search. ### Findings
- **medium** N-1. The substring tier can still bury content matches (§3 Match kind and Rank; FR-9; FR-11; SM-3; SM-C1). **substring** needs only that "every query word appears somewhere in the name", with no minimum word length, and it ranks above **content**. A one-word query such as `tax` substring-matches `syntax.md`, `taxi_receipt.pdf`, and any name containing those letters. All of them outrank the text file that actually contains "tax". A two-letter word like `q3` or `at` matches widely. FR-10 sets length floors for typo tolerance ("3 letters or fewer get no typo tolerance"), but substring has none. SM-3's fixtures use words that "appear only inside the target", so the measurement never meets this competition. SM-C1 only measures false matches on the SM-2 (name) fixtures. This is the residual of adversarial H-5. *Fix:* give substring a floor, for example "a query word of 3 or fewer characters matches only as a token or token beginning, never as a substring". Add SM-3 fixtures in which competing substring and typo name matches exist, and extend SM-C1 to cover them.
- **medium** N-2. SM-8 is measured inside SM-1, but the two protocols conflict (§8 SM-1 Protocol, SM-8; FR-1). SM-8 says "In the SM-1 test, at least 4 of 5 users complete the MyFiles guide … and the chosen folder opens on the first try". SM-1, though, uses a *seeded* folder "in a location the operating system's search indexes", with the clock running from the start state. If participants do the MyFiles setup (create `C:\MyFiles`, change the browser's download location), it either lands inside SM-1's timed tasks and inflates Find's time, or the seeded folder isn't the MyFiles folder and SM-8 tests nothing real. On Windows, `C:\MyFiles` is typically outside Windows Search's default indexed locations. The recommended folder may therefore be unfair to the OS-search arm in the other direction. *Fix:* run SM-8 as a separate, untimed step before SM-1, with its own instruction. State whether the SM-1 seeded folder is the MyFiles folder, and if it is, that it has been added to the OS index.

## Done-ness clarity — adequate

The matching core is now precise enough to test. The token rules, the query split, the five match kinds, the rank order, the OSA distance, the length-based edit limits, and the name-date formats all come with worked examples. I checked every FR-9, FR-10, and FR-11 example against the §3 definitions, and each one yields the labelled kind and order. For example, `annualreport2025` is a single token, so `report` is **substring**. `Reports` has the token beginning `Report`, so `report` is **partial** and `reprot` is **typo**. `budgte` is 1 swap from `budget`, so it is **typo** and ranks below `notes.txt` (content). FR-12 and EARS-04 agree on both message strings and the "listing or indexing" condition. What holds this at *adequate* are the two new FRs and one gap in the typo rule. A story writer will hit all three.

### Findings
- **medium** N-3. FR-22 doesn't say what the user sees during a rebuild (FR-22; FR-15; FR-12; NFR-4). "**Rescan** reruns listing and indexing, and keeps the query, filters, and selected file entry … During a rescan, the result list shows *still updating*, and EARS-04 applies." It doesn't say whether the old folder tree, result list, and content index stay visible until the new ones replace them, or whether they are cleared and refilled. "EARS-04 applies" suggests clearing, because EARS-04 only shows when nothing matches. Clearing means a user mid-task loses the file they were looking at from the result list for up to 60 seconds. Keeping both indexes risks going over the 200 MB limit. The answer changes the UX and the architecture, and the FR's tests can't be written without it. *Fix:* state one behavior. For example: "Existing file entries stay in the result list until listing confirms or removes them. Content matches from the previous index stay until their file is re-indexed. EARS-04 applies only if the result list is empty." Or say explicitly that rescan clears and rebuilds.
- **medium** N-4. Typo tolerance against token beginnings has no defined prefix length (FR-10; addendum "Typo distance"). FR-10 now says a query word can match "the beginning of a token, despite small English spelling errors". The only length rule is in the addendum: "against token prefixes of a similar length". So it isn't testable from the PRD. Does `budgte` (6 letters, 1 edit) match `budgeting.xlsx` as **typo**? Does `from` match `format` (prefix `form`, 1 swap)? Does `repo` match `rep`? Each answer moves SM-2 and SM-C1. *Fix:* in FR-10, compare a query word against the token prefix of the *same length* as the query word, and add one positive example and one negative example.
- **medium** N-5. FR-21 can't keep NFR-5's and NFR-1's promise for a PDF opened in a tab (FR-21; NFR-5; NFR-1; SM-6). NFR-5 says "Previewed **and opened** content is shown as inert content: it can never run scripts or reach the network." FR-21 opens a PDF "in a new browser tab". That tab is the browser's own PDF viewer, which Find doesn't control: links inside the PDF are clickable, and the viewer may run some document scripts. The addendum's `text/plain` trick protects text files only. The same gap applies to in-app PDF preview if pdf.js scripting and link annotations aren't disabled (adversarial M-5, still open). *Fix:* scope NFR-5. In-app previews are inert (pdf.js scripting off, links inert). For a PDF opened in a browser tab, say that it is shown by the browser's viewer, outside Find's guarantee, and exclude user-initiated link clicks from NFR-1 and SM-6. Alternatively, open PDFs in a Find-controlled viewer tab.
- **medium** N-6. The Copy location hand-off is unverified (FR-21; UJ-1 Resolution; §3 Location; SM-1 Timing). UJ-1 ends with Daniel copying `MyFiles/Clients/Acme/Project_Report_Sep.pdf`, pasting it into File Explorer, and opening the file in Acrobat. The FR-21 hint says to "Use **Copy location** to find it in File Explorer or Finder." The location is relative, because the Glossary says browsers don't reveal the full path. Whether pasting a relative path into the Explorer address bar or Finder's Go to Folder resolves depends on the current folder, and on macOS it generally won't work. SM-1 counts this step as a valid stop condition. This is the residual of adversarial C-2. *Fix:* add an OQ-1 spike item, "verify the Copy location paste flow on Windows and macOS". Reword UJ-1 and the FR-21 hint to the flow that works. Consider copying the file name too (pasted into File Explorer or Finder search, it is location-independent).
- **low** N-7. The EARS-03 rev. 1 and EARS-04 conditions overlap after a cancel during listing (FR-12; FR-13; EARS file). EARS-03 rev. 1 fires when "listing and indexing have completed, **or indexing was cancelled**". EARS-04 fires "while listing or indexing is in progress". If the user cancels indexing while listing is still running, both conditions are true and they prescribe different messages. FR-12's cancel bullet has the same gap. *Fix:* in FR-12 and the EARS file, write "or listing has completed and indexing was cancelled".
- **low** N-8. Whether the extension takes part in name matching is unstated (§3 Token; FR-9). Dots split tokens, so `report.pdf` yields the token `pdf`, and the query `pdf` would make every PDF an **exact** match. The query `doc` would make every DOCX a **partial** match. *Fix:* state whether the extension is a matchable token. For example, "the extension is matched but ranks below a base-name match", or "the extension is excluded; use the type filter".
- **low** N-9. A concatenated query doesn't match a separated name (§3 Query, Token; FR-9). `annualreport` against `Annual Report 2025.pdf` is not exact or partial. It isn't substring either, because the name contains "annual report", not "annualreport". Nor is it typo: the word has 12 letters, so it tolerates 2 edits, and it is far more than 2 from both tokens. This is the mirror image of the fixed F-02, and it is common when users retype a name from memory. *Fix:* also compare each query word against the name with its separators removed, as a substring, or list this case in §7.2.
- **low** N-10. FR-22 has two smaller gaps. "Listed at HH:MM" doesn't say whether it is the start or the end of listing, or the time format. "This file is no longer in the folder" is defined only after a rescan. Previewing or opening a file deleted *between* rescans, which fails on read, has no defined message. That was part of adversarial H-7's fix. *Fix:* say "time listing completed, local time". Extend the message to any preview or open that fails because the file is gone.
- **low** N-11. The index limit's unit doesn't match its measure (NFR-4). "200 MB of extracted text, measured … as the total length of stored searchable content". A length in characters is not a byte count; the addendum offers "characters … (or UTF-16 length × 2 bytes)", which differ by a factor of 2. *Fix:* state the limit in one unit, for example "100 million characters (about 200 MB as UTF-16)".

### Findings
- **low** N-13. The **content** match kind contradicts its own tie-break rule (§3 Match kind). **content** is defined as "a content-only match", which by definition is "a content match that is not also a name match". The next sentence says "A file entry that is both a name match and a content match gets the better of the two kinds". For a **typo** name match that is also a content match, the better kind is **content**, which the entry can't have under the definition. Stories will copy the contradiction. *Fix:* define **content** as "a content match whose name match kind, if any, ranks below content (that is, typo or none)", or simply "a content match not labelled with a better name kind".

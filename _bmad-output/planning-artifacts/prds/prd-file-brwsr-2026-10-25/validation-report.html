This is a strong, build-ready PRD, and better than the version reviewed in review-rubric-v1.md. The edits closed every high finding in the rubric and EARS reviews. Typo distance is now defined (Damerau-Levenshtein, OSA). Query words are split by the same rules as names. A substring match kind honors EARS-01's "contain". EARS-03 rev. 1 and EARS-04 are traced in §0 and carried by FR-12. The deliberate DOCX trade-off now reads the same way in the Vision, §2.2, UJ-1, FR-16, §7.2, and SM-1, so it counts as an accepted risk rather than a defect. The new match kinds, rank order, and FR examples agree with one another; every worked example checks out. What remains at risk is narrower. The substring tier has no minimum word length and ranks above content, so short queries can still bury the content matches the thesis depends on. FR-22 doesn't say what happens to the existing result list during a full rebuild. FR-21's open-in-tab can't keep NFR-5's promise for PDFs, and the UJ-1 hand-off relies on pasting a relative location into File Explorer, which is unverified. None of this blocks UX, but FR-10, FR-21, and FR-22 should be tightened before stories are written.

The EARS re-check (review-ears.md) has one high finding, N-01: when indexing is cancelled while listing is still running, EARS-03 rev. 1 ("No matching files found") and EARS-04 ("No matches yet. Still searching…") both apply, so no implementation can pass both. The rubric rates the same issue as low (N-7). A one-line fix has been proposed to the user and is pending approval: make listing completion mandatory in the "finished" condition ("listing has completed, and indexing has completed or was cancelled") in the EARS file and FR-12. The grade follows the rubric, as validate.md specifies; until that fix lands, this is the one open requirements conflict.

The adversarial review (review-adversarial-general.md) covered the previous PRD version and is not a current reviewer. Its critical and high findings were tracked in the rubric's Prior findings status table: 10 resolved, 2 partially resolved, 2 accepted-risk, 0 open.

Strategic coherence

strong

The thesis is now narrower and fully coherent with scope and metrics. medium

N-1. The substring tier can still bury content matches

§3 Match kind, Rank; FR-9; FR-11; SM-3; SM-C1
Substring needs only that "every query word appears somewhere in the name", with no minimum word length, and it ranks above content. tax substring-matches syntax.md and taxi_receipt.pdf, all outranking the text file that actually contains "tax". SM-3's fixtures never meet this competition; SM-C1 only measures name fixtures. Residual of adversarial H-5.
Fix: Give substring a floor (a query word of 3 or fewer characters matches only as a token or token beginning). Add SM-3 fixtures with competing substring and typo name matches, and extend SM-C1 to cover them.
medium

N-2. SM-8 is measured inside SM-1, but the two protocols conflict

§8 SM-1 Protocol, SM-8; FR-1
If participants do the MyFiles setup, it lands inside SM-1's timed tasks and inflates Find's time; if not, SM-8 tests nothing real. C:\MyFiles is typically outside Windows Search's default indexed locations, which may be unfair to the OS-search arm.
Fix: Run SM-8 as a separate, untimed step before SM-1. State whether the SM-1 seeded folder is the MyFiles folder and, if so, that it has been added to the OS index.

Done-ness clarity

adequate

The matching core is now precise enough to test. The token rules, the query split, the five match kinds, the rank order, the OSA distance, the length-based edit limits, and the name-date formats all come with worked examples, and every FR-9, FR-10, and FR-11 example yields the labelled kind and order. FR-12 and EARS-04 agree on both message strings and the "listing or indexing" condition. What holds this at adequate are the two new FRs and one gap in the typo rule.

medium

N-3. FR-22 doesn't say what the user sees during a rebuild

FR-22; FR-15; FR-12; NFR-4
Unclear whether the old tree, result list, and content index stay visible until replaced, or are cleared and refilled. "EARS-04 applies" suggests clearing, which loses the user's file for up to 60 seconds; keeping both indexes risks the 200 MB limit.
Fix: State one behavior, e.g. existing entries stay until listing confirms or removes them, and EARS-04 applies only if the result list is empty; or say explicitly that rescan clears and rebuilds.
medium

N-4. Typo tolerance against token beginnings has no defined prefix length

FR-10; addendum "Typo distance"
The only rule is the addendum's "token prefixes of a similar length". Does budgte match budgeting.xlsx? Does from match format? Each answer moves SM-2 and SM-C1.
Fix: In FR-10, compare against the token prefix of the same length as the query word; add one positive and one negative example.
medium

N-5. FR-21 can't keep NFR-5's and NFR-1's promise for a PDF opened in a tab

FR-21; NFR-5; NFR-1; SM-6
A PDF opened in a new tab uses the browser's own viewer, which Find doesn't control: links are clickable and some document scripts may run. The same gap applies to in-app preview if pdf.js scripting and links aren't disabled (adversarial M-5).
Fix: Scope NFR-5: in-app previews are inert; a PDF opened in a browser tab is outside Find's guarantee, and user-initiated link clicks are excluded from NFR-1 and SM-6. Or open PDFs in a Find-controlled viewer tab.
medium

N-6. The Copy location hand-off is unverified

FR-21; UJ-1 Resolution; §3 Location; SM-1 Timing
The copied location is relative (MyFiles/Clients/Acme/…). Whether pasting it into Explorer or Finder's Go to Folder resolves depends on the current folder, and on macOS it generally won't. SM-1 counts this as a valid stop. Residual of adversarial C-2.
Fix: Add an OQ-1 spike item to verify the paste flow on Windows and macOS; reword UJ-1 and the FR-21 hint to the flow that works; consider copying the file name too.
low

N-7. EARS-03 rev. 1 and EARS-04 overlap after a cancel during listing

FR-12; FR-13; EARS file
If the user cancels indexing while listing is still running, both conditions are true and prescribe different messages. Same issue as EARS review N-01, which rates it high.
Fix: In FR-12 and the EARS file, write "or listing has completed and indexing was cancelled".
low

N-8. Whether the extension takes part in name matching is unstated

§3 Token; FR-9
Dots split tokens, so pdf would make every PDF an exact match, and doc every DOCX a partial match.
Fix: State whether the extension is a matchable token (e.g. matched but ranked below a base-name match, or excluded in favor of the type filter).

N-9. A concatenated query doesn't match a separated name

§3 Query, Token; FR-9
annualreport against Annual Report 2025.pdf matches no kind. Mirror image of the fixed F-02, and common when users retype a name from memory.
Fix: Also compare each query word against the name with separators removed, as a substring, or list this case in §7.2.
low

N-10. FR-22 has two smaller gaps

FR-22
"Listed at HH:MM" doesn't say start or end of listing, or time format. "This file is no longer in the folder" is defined only after a rescan, not for a file deleted between rescans.

NFR-4

high

N-01. EARS-03 rev. 1 and EARS-04 overlap when indexing is cancelled before listing finishes

EARS-03 rev. 1, EARS-04; FR-12 bullets 2–3; FR-13; FR-22
Listing and indexing both start on access, so the user can cancel indexing while listing runs. Both conditions are then true and require different messages in the same area. Two requirements conflict, and no implementation can pass both. Choosing EARS-03 re-creates the false "no match" the revision was meant to remove. "Indexing was cancelled" is also sticky across a rescan. Fix proposed to the user; pending approval.
Fix: In the EARS file and FR-12: "the search has finished (listing has completed, and indexing has completed or was cancelled)". In FR-22, state that a rescan clears the cancelled state.
medium

N-02. A non-empty query with no query words is undefined, and literally matches every file

§3 Query, Token, Name match; FR-12; EARS-01, EARS-03
A term such as -, ..., or spaces only is non-empty to EARS but yields zero query words, so "every query word matches" is vacuously true for every file. Treating it as empty is reasonable but an unlogged deviation from "non-empty".
Fix: Add to §3: a query that yields no query words is an empty query. Record this reading of "non-empty" in the §0 traceability table.
medium

N-03. The EARS-04 acceptance test cannot be reproduced reliably as written

EARS-04 acceptance test; FR-12 bullet 2
Indexing one small PDF takes milliseconds, so a tester cannot reliably type xyz123 before it finishes. The test is timing-dependent.
Fix: Name a deterministic method: a test hook that pauses the indexer, or a fixture large enough that indexing visibly runs. State that the in-progress state ends when the FR-15 still updating indicator disappears.
low

N-04. No match kind for a query word that spans a token boundary

§3 Match kind; FR-11
tre matches ProjectReport.txt across Project|Report, but it is not exact, partial, or "inside a token", so no kind applies, while FR-11 requires every result to be labelled.
Fix: Define substring as "every query word appears in the name, and at least one appears neither as a token nor as a token beginning".
low

N-05. EARS form quality of the revised statements

EARS-03 rev. 1, EARS-04
EARS-03 rev. 1 puts a state inside the If clause. EARS-04 is labelled state-driven but is a complex While + If requirement with no "then", and the transition to EARS-03 lives only in its acceptance test.
Fix: Relabel EARS-04 "Complex" and write "…, if …, then the system shall …". Restate EARS-03 rev. 1 in While/If form.
low

N-06. The EARS-04 transition wording differs slightly between the files

EARS-04 expected result; FR-12 bullet 2
EARS: "Once indexing completes". FR-12: "once both complete". Equivalent in practice, but the texts differ.
Fix: Align the EARS file to "Once listing and indexing complete".
